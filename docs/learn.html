From first principles

The concepts, in plain language

You do not need a computer-science background to follow these pipelines. Nine ideas explain why they are built the way they are, and every technical word is defined below with an everyday comparison.

Nine ideas behind all eight pipelines

01

Every pipeline is a line of stations

Data goes in one end, passes stations in a fixed order - read it, clean it, check it, decide, build the output, check the output, release it, keep a copy - and comes out the other end. Each station does one job. When something goes wrong you know exactly which station caught it.

Why: Small steps are easy to test one at a time, and a failure points at a single place.

Where: Every project. Atlas has the clearest line - check, freeze, render, verify, publish.

02

All the data is invented, on purpose, and repeatable

A generator program makes up every organisation, person and number from a starting number called a seed. Same seed, same data, byte for byte. It also plants specific mistakes so the checks have something real to catch, and the tests know exactly what should be caught.

Why: Nothing private can leak, anyone can rerun it, and every test result can be checked against a known answer.

Where: Each project's synth.py or sources.py; the "same seed, same bytes" test in every project.

03

Check before anything is used, and name the problem

Before data becomes an output, rules run over it. A blocking problem stops the run and says which record and why. An advisory problem is reported but does not stop it. Nothing is silently fixed or silently skipped.

Why: A bad record in a published file spreads to everyone who uses it; catching it early is cheap.

Where: Atlas's rule registry, OpenBadge's three layers of checks, Regional's findings, SafeSite's return checks.

04

The computer never guesses about what needs judgment

When two sources disagree and no rule settles it, or two names are almost the same, the pipeline holds the case and asks a named person. Their decision, with their role and reason, is recorded. Anything that is published also waits for a named approval.

Why: An automatic guess is wrong some of the time, and a wrong merge or publish is hard to undo.

Where: MasterRecord holds, ReconcileHub cases, approvals in Atlas, Regional, SafeSite and OpsPilot.

05

Nothing good is ever overwritten

Releases, approved reports and snapshots are versioned. A new version is written next to the old one, never on top of it. A second approval of the same thing changes nothing; a real revision becomes version 2 with a reason.

Why: If the new version turns out wrong, the old one is still there, untouched.

Where: OpenBadge releases, Atlas periods, Regional v1/v2, SafeSite finals, ReconcileHub supersede.

06

Running it twice is safe

Every pipeline can be run again on the same inputs without duplicating anything: the same reminder is not drafted twice, the same decision is not applied twice, the same roster is not approved twice.

Why: Real jobs get rerun - after a crash, by a scheduler, by someone pressing the button twice.

Where: SafeSite reminders, MasterRecord decision hashes, ReconcileHub NOTHING NEW, OpsPilot checkpoints.

07

Fingerprints prove what happened

Every important file gets a SHA-256 fingerprint. Manifests list inputs and outputs with their fingerprints. A restore or rollback first re-checks the fingerprints; if a file has changed, it refuses.

Why: You can prove which data produced which output, and you cannot restore something that was tampered with.

Where: Run manifests in every project; LedgerGuard and Atlas restores; OpenBadge's pointer.

08

Release all at once, or not at all

Outputs are built and checked in a staging area first. Releasing them is one quick swap - a rename or a pointer change - so readers see the whole new version or the whole old one, never half of each.

Why: A crash half way through copying files would otherwise leave a mixture nobody can trust.

Where: Atlas publish, OpenBadge pointer, LedgerGuard daily sets, ReconcileHub snapshots.

09

Every claim has a test, and every run leaves evidence

Each behaviour described in a README is checked by an automated test, and GitHub runs all the tests on fresh Linux and Windows machines after every change. Every run writes a manifest and readable reports.

Why: Saying "it works on my machine" is not proof; a test anyone can rerun is.

Where: 108 tests across eight projects, 11 more for the Lab; the CI badge on the repository; the experiments that found three real bugs.

Glossary

advisory findingA problem worth reporting that does not stop the run.Like: A note that the tyres will need replacing soon.
agentSoftware that decides which actions to take, within the tools and permissions it is given.Like: An assistant who may only use the tools in their kit and must ask before spending money.
append-onlyNew entries can be added, but existing ones can never be changed or deleted.Like: Writing in pen in a bound notebook.
approval gateA point where the pipeline waits for a named person to say yes before doing something consequential.Like: A permission slip a parent must sign.
archiveOlder versions kept, unchanged, for the record and for restoring.Like: Last year's yearbooks on the shelf.
atomicA change that happens completely or not at all - never half way.Like: Swapping a whole tray of cups at once rather than one cup at a time while people drink.
audit trailA record of what happened, when, by whom and why.Like: A diary nobody is allowed to tear pages out of.
automationHaving a computer do repeatable steps so a person only handles the decisions that need judgment.Like: A dishwasher does the washing; you still decide what goes in.
backupA copy kept so the original can be restored if something goes wrong.Like: A spare key.
blocking findingA problem serious enough that the pipeline stops and publishes nothing until it is fixed.Like: A failed brake inspection: the car does not leave the garage.
checkpointA saved record that a step finished, with proof of what it produced, so a stopped run can resume.Like: A save point in a video game.
CIContinuous integration: every time code is pushed, a fresh machine installs it and runs all the tests.Like: An inspector who re-checks the whole building every time anything is changed.
CLICommand-line interface: a program you control by typing commands.Like: Ordering by saying exactly what you want, instead of pointing at a menu.
columnOne kind of fact recorded for every row, such as an expiry date.Like: The 'homeroom' column on the roster.
constraintA rule the database enforces itself, such as 'never blank' or 'must be one of these words'.Like: A form field that only accepts a date.
CSVA plain text file of rows, with commas between the columns. Almost every system can export one.Like: A spreadsheet saved as plain text.
databaseAn organised store of information made of tables, where the computer can enforce rules about what is allowed in.Like: A filing cabinet that refuses to accept a form with a box left blank.
dry runA rehearsal that shows exactly what would change, without changing anything.Like: Reading the recipe aloud before cooking.
ETLExtract, Transform, Load: take data out of sources, clean and reshape it, put it where it will be used.Like: Collect ingredients, prepare them, plate the meal.
exceptionA record that breaks a business rule and needs someone's attention.Like: A library book that is overdue.
fixtureA prepared set of data used by tests, so every test starts from the same known state.Like: A science experiment that always starts with the same measured ingredients.
foreign keyA column that must match a primary key in another table, so a record can never point at something that does not exist.Like: A library card number on a checkout slip must belong to a real card holder.
formulaA cell that calculates its value from other cells, so the total always matches its parts.Like: A calculator built into the page.
fuzzy matchTwo values that are similar but not identical, such as names with one letter different.Like: 'Jon Smith' and 'John Smith' on two forms.
hashA short fingerprint computed from a file's exact bytes. Change one character and the fingerprint changes completely.Like: A wax seal: if it is broken or different, someone opened the letter.
holdPausing a decision for a person instead of letting the computer guess.Like: 'Ask a teacher' rather than flipping a coin.
idempotentRunning the same thing twice gives the same result as running it once; nothing is duplicated.Like: Pressing a lift button twice does not call two lifts.
indexA lookup structure that lets the database find rows by a column quickly.Like: The index at the back of a book.
ingestRead data in from a source and record exactly what arrived.Like: Signing for a delivery and noting how many boxes came.
JSONA text format for structured data - lists and labelled values - that programs exchange.Like: A packing list with headings and items under each heading.
JSON SchemaA machine-readable description of what a JSON file must look like, used to check a file automatically.Like: A checklist an inspector ticks against every package.
manifestA list of every file a run used or produced, with each file's hash, plus who, when and what version.Like: A packing slip that lists every item in the box and its serial number.
migrationA numbered script that creates or changes the database's structure, applied once and in order.Like: Renovation plans numbered 1, 2, 3 so the builder never does step 3 before step 2.
normaliseTurn the many ways the same thing is written into one standard form, keeping the original too.Like: Writing every phone number the same way in an address book.
orchestrationCoordinating many jobs: their order, what each waits for, and what happens when one fails.Like: An air-traffic controller for software jobs.
outboxA folder of drafted messages that nobody has sent. A person reviews and sends them.Like: Letters written and stamped but still on your desk.
pipelineA series of steps that runs in a fixed order, where each step takes the last step's result and does one job with it.Like: An assembly line: one station checks, the next packs, the next labels.
pointerA small file that says which version is the current one. Changing it switches everyone to another version at once.Like: A sign saying 'today's menu is on board 3'.
precedenceWhich source wins when two sources give different values.Like: A referee's call overrides a player's opinion.
primary keyThe column whose value is different for every row, so each row can be found exactly.Like: A student ID number: two students may share a name, never an ID.
publishMake an output available to the people who use it.Like: Putting the newsletter in the mailboxes.
QAQuality assurance: checks that the data and the outputs are right before anyone relies on them.Like: A teacher checking answers before grades go home.
quarantineA separate folder where a suspicious file is moved so nothing uses it.Like: Setting aside a dented can instead of putting it on the shelf.
reconciliationComparing two lists that should agree and explaining every difference.Like: Checking your bank statement against your own records.
repositoryA project folder whose complete history of changes is kept, usually on GitHub.Like: A document with every earlier draft saved.
resumeCarry on a stopped run from the first step that is not provably finished.Like: Opening the book at your bookmark, not at page one.
rollbackGoing back to an earlier version that is known to be good.Like: Undo, but only to a version you have checked.
rowOne item in a table, such as one badge or one venue.Like: One line on the roster.
rule registryOne file listing every check, how serious it is, why it exists and how to fix it.Like: A rulebook, rather than rules scattered across people's heads.
schemaThe blueprint of a database: which tables exist, which columns they have, and what values are allowed.Like: The design of a form before anyone fills it in.
seedA starting number for the random generator. The same seed always produces exactly the same invented data.Like: A shuffle you can repeat exactly by remembering how you shuffled.
SHA-256The specific fingerprint method used here. It produces 64 letters and digits for any file.Like: A particular brand of tamper-evident seal.
SQLiteA small database that lives in a single file on your computer. No server needed.Like: A notebook you carry, rather than a library you have to visit.
stagingA holding area where outputs are built and checked before they are released.Like: The kitchen pass, where plates wait to be checked before going to the table.
synthetic dataData invented by a program for practice or demonstration. None of it describes real people or places.Like: Crash-test dummies instead of real drivers.
tableRows and columns of one kind of thing, like a spreadsheet tab. One row per item, one column per fact about it.Like: A class roster: one row per student, columns for name, grade, homeroom.
testA small program that runs the real code on known data and checks the result is exactly what it should be.Like: A fire drill: you find out if the plan works before you need it.
tool registryThe complete list of actions an orchestrator or agent is allowed to take, each with its inputs and effect.Like: The list of jobs a new employee is trained and allowed to do.
validationChecking that something follows the rules before it is used.Like: A bouncer checking IDs at the door.
workbookAn Excel file; it can hold several sheets (tabs).Like: A binder with several sections.
